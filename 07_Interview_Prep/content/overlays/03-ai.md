## AI System Design Patterns [Core]

> AI system design rounds test whether you can turn a working LLM demo into a system that strangers can rely on. Seven patterns keep coming up: observability, caching, agentic evals, RAG, fine-tuning, user feedback loops and guardrails. A weak answer lists all seven as a checklist. A strong answer picks the ones the problem needs, puts them in a defensible order, names what each one costs, and explains how you would know each one is working.

### In plain words
A demo is one cook making one dish for a friend; a production AI system is a restaurant serving hundreds of strangers every night. Observability is the order ticket that records every dish, how long it took and what it cost, and caching keeps the most popular dishes ready so nobody waits. Evals are the taste test before a plate leaves the kitchen, RAG hands the cook the house recipe book, and fine-tuning sends the cook on a course when the recipe book is not enough. Feedback loops read the customer reviews and change the menu, and guardrails are the head chef at the pass who stops a bad plate from reaching the table.

### Concepts you must understand
- Observability solves "we cannot see why it failed": one trace per request with prompt version, model, tokens, cost, latency, retrieved chunk ids and tool calls; it costs storage, instrumentation time and a PII risk in logs that needs redaction and retention rules.
- Caching solves repeated work, cutting latency and API spend; it costs freshness, adds the risk of a wrong or cross-tenant hit, and makes invalidation part of every release.
- Agentic evals solve "did the agent pick the right tool and finish the job"; they cost labelled tasks, a sandbox to check outcomes against, and several trials per task because runs are not deterministic.
- RAG solves missing, private or fast-changing knowledge and makes answers citable; it costs an ingestion pipeline, an index to operate, retrieval latency, and new failure modes such as retrieval misses, permission leaks and instructions hidden inside documents.
- Fine-tuning solves consistent behaviour, format or tone, or a cheaper small model for a narrow task, once prompting and RAG have plateaued; it costs curated data, training and hosting, re-tuning when the base model changes, and it is a poor way to add facts that change.
- User feedback loops solve an eval set that goes stale and failure modes nobody predicted; they cost UI work, labelling time, privacy and consent handling, and bias from who bothers to respond.
- Guardrails solve unsafe, off-policy, malformed or leaked output and limit what a hijacked model can do; they cost latency and false positives that block good answers, and they need their own evals.
- A sensible default order: observability and a small eval set first because they measure everything else, then RAG, guardrails sized to risk, agentic evals once tools exist, caching once traffic shows repetition, the feedback loop, and fine-tuning last.

### Q. Design an AI customer-support assistant. Which of the seven patterns do you apply, and in what order?
**Short answer (45 seconds):** Scope first: help-centre answers, order and account lookups, tickets, human handoff, and refunds only with approval. Then the order: tracing and a small golden set on day one, because they judge every later change; RAG over the help centre with citations; guardrails sized to the actions; agentic evals as soon as tools exist; caching once traffic shows repeated questions; a feedback loop that feeds the eval set; fine-tuning last, only for a measured gap that prompts and retrieval cannot close.

**Deeper explanation:**

```text
user -> gateway (auth, tenant, rate limit)
     -> input guard (injection screen, PII redaction)
     -> cache (exact, then semantic; generic FAQ routes only)
     -> router: FAQ | account question | action | human
     -> RAG: hybrid search + rerank over help centre, ACL filtered
     -> LLM with tools (read-only by default, refund needs approval)
     -> output guard (schema, policy, citation check)
     -> stream answer + feedback buttons
every hop writes a span: prompt version, model, tokens, cost, chunk ids, tool calls
```

RAG beats fine-tuning because policies change weekly and answers need a source anyone can check. Caching suits "how do I reset my password", never "where is my order", so cacheability belongs to the route. Guardrails follow the blast radius: FAQs need injection screening and output checks; refunds need user-scoped tool permissions, an approval step and an audit log. A realistic fine-tuning candidate is a small intent router trained on labelled conversations from the feedback loop, cutting cost and latency without touching the answer model.

**Follow-ups they will ask:**
- What is the success metric?: Resolution without human escalation, with cost per resolved conversation and wrong-escalation rate as guardrails.
- What do you cut for an MVP?: Semantic cache and fine-tuning; keep tracing, the golden set, RAG with citations and guardrails on actions.
- Handoff?: An escalation tool passes a summary and sources, triggered by low confidence, policy topics or the customer asking.

**Mistakes to avoid:**
- Reciting all seven patterns as an unordered checklist.
- Fine-tuning on the help centre to "teach" policies that change every week.

### Q. How do you design caching for an LLM application, and what can go wrong?
**Short answer (45 seconds):** Three layers. An exact-match response cache on normalised input, a semantic cache that reuses an answer for a near-duplicate question, and provider prompt caching that reuses the computation over a stable prompt prefix without changing the output. The first two carry tenant, permission scope, prompt version and model in the key, so a prompt or model change invalidates them automatically. What goes wrong: stale answers, wrong semantic hits, cross-tenant leaks, one bad answer cached and served to everyone, and stampedes when a hot entry expires.

**Deeper explanation:**

| Layer | Reuses | Saves | Main risk | Invalidated by |
|---|---|---|---|---|
| Exact response | Answer for identical input | Whole call | Stale answer | TTL, document, prompt or model change |
| Semantic | Answer for a similar question | Whole call | Wrong hit on a near-miss | Same, plus a tuned threshold |
| Prompt prefix | Provider's work on a repeated prefix | Input cost, time to first token | Silent misses only | Any byte change in the prefix |

Key shapes, thresholds and chunk verification are covered in this track's sections "Advanced RAG Patterns" and "Cost & Latency at the Application Layer". Three design rules to add: write to the cache only after the output guardrail passes, so a bad answer is never replayed; keep a purge by entry and by source document, because one bad entry can reach thousands of users; never cache routes with side effects or personal data. Protect hot entries from stampedes with request coalescing (Backend track, section "Caching").

**Follow-ups they will ask:**
- Where does it live?: Redis for exact entries, Redis vector search or pgvector for semantic ones, namespaced per tenant.
- Does prompt caching need invalidation?: No, it misses on its own when the prefix changes; monitor the cached-token ratio.
- What about A/B tests?: Key the cache by experiment arm, or the control arm serves treatment answers.

**Mistakes to avoid:**
- One global semantic cache shared across tenants.
- Caching before the output guardrail, so a single bad answer is served to everyone.

### Q. How do you close the loop from user feedback to a better system?
**Short answer (45 seconds):** Feedback is only useful when it is joined to the trace that produced it: prompt version, model, retrieved chunks and tool calls. I capture explicit signals (thumbs with a reason code, corrections) and implicit ones (rephrasing, regenerating, escalating, abandoning), triage them weekly into failure types, turn each type into eval cases first, and then route the fix to the pattern that owns it. Every fix ships through the same eval gate and canary as any other change; nothing reaches production straight from feedback.

**Deeper explanation:** The design work is routing each failure to the part of the system that owns it:

| What the trace shows | Fix goes to |
|---|---|
| Right document never retrieved | RAG: chunking, query rewriting, hybrid search, or a missing document |
| Right chunks retrieved, answer still wrong | Prompt or model, plus a new eval case |
| Unsafe or off-policy answer | Guardrail rule and a red-team eval case |
| Correct once, outdated now | Cache invalidation or index freshness |
| Wrong tool or wrong arguments | Tool descriptions and an agentic eval case |
| Same format gap across thousands of examples | Fine-tuning dataset, once prompts plateau |

Each feedback row stores trace id, signal, reason code and any correction, so a weekly query ranks failure types by volume and severity; support-staff corrections are the richest signal because the right answer comes attached. Cadence, labelling and bias are covered in the MLOps & LLMOps track, section "Feedback Loops & the Data Flywheel".

**Follow-ups they will ask:**
- Users rarely click thumbs?: Lean on implicit signals and a sampled review queue, and compare rates between versions rather than as absolute quality.
- When does feedback become training data?: When thousands of curated, consented, redacted examples show a consistent gap that prompt and retrieval changes have not closed.
- How do you avoid optimising for flattery?: Pair feedback with correctness judges and escalation outcomes, never thumbs alone.

**Mistakes to avoid:**
- A thumbs-down counter on a dashboard with no link to traces.
- Automatically editing prompts or the index from feedback without the eval gate.

### Q. How do you know your agent picked the right tool and reached the right outcome?
**Short answer (45 seconds):** Three separate checks, because one end-to-end pass rate cannot tell you what broke. Tool-selection accuracy: for recorded states, is the chosen tool the labelled correct one. Trajectory checks: did the run respect constraints such as "look up before you write", no forbidden tools, no repeated identical calls, under a step cap. Outcome checks: query the database or API to confirm the world is in the right state, never trusting the agent's own "done". Each task runs several times, and I report how often it passes every time.

**Deeper explanation:**

```text
check            question                                   grader
tool selection   given this state, is this the right tool?  labelled step, confusion matrix
trajectory       was the path acceptable?                   constraints on order, tools, steps
outcome          is the world in the right state?           query the DB or API in a sandbox
```

Tool selection is the cheapest to evaluate: freeze states from production traces, label the right action (a tool, "ask the user" or "no tool"), and replay only the next decision. A confusion matrix shows which tools get mixed up; if `search_orders` and `get_order` are confused, the fix is clearer descriptions or merging the tools, not a longer system prompt. Outcome checks need a seeded sandbox so a checker can read the resulting refund row or ticket. Online, sample traces and watch tool error rate, calls whose result was never used, steps per task and escalations. Matching modes, tool precision and recall code, and `pass^k` are in the Agents track, section "Agent Reliability & Evaluation".

**Follow-ups they will ask:**
- Right outcome through a bad path?: Still a failure if it broke a constraint, such as writing before verifying; outcome-only evals hide risk.
- Right path, wrong outcome?: Usually a tool bug or ignored tool output; read the tool result in the trace.
- How many tasks to start?: A few dozen real tasks from traces, growing with every production failure.

**Mistakes to avoid:**
- Grading the agent's final "Refund issued" message as proof of success.
- Only end-to-end evals, so tool choice, arguments and tool bugs cannot be told apart.

### Q. What does a 45-minute AI system design answer look like?
**Short answer (45 seconds):** The same disciplined agenda as any system design round, with the AI-specific parts carrying the score: requirements including a quality bar, latency and cost per request; the data, its freshness and its permissions; the request path with retrieval, tools and model choice; how you would know it works, meaning evals per stage and a CI gate; guardrails; observability and cost. Designing under pressure, out loud, is what gets judged, more than certificates, so I rehearse the agenda until it is automatic.

**Deeper explanation:**

```text
0-5    requirements: users, tasks, allowed actions, quality bar, p95 latency, cost per request, data sensitivity
5-10   data: sources, volume, freshness, permissions; what the model must look up vs already knows
10-20  request path: retrieval (chunking, hybrid search, rerank), tools, model choice and routing
20-30  evals: golden set, retrieval recall@k, faithfulness, task success, CI gate, A/B plan
30-38  guardrails and failure: injection, PII, tool permissions, approvals, fallback when the provider is down
38-45  observability and cost: traces, cost per request, caching, rollout (shadow, canary)
```

Model choice needs a reason: a hosted frontier model for the hard step, small models for routing and extraction, open weights only when residency or cost at scale demands it. Do one cost estimate out loud: 10,000 conversations a day at 6 turns and 4,000 input tokens per turn is 240 million input tokens a day; then say what prompt caching, history trimming and routing do to that number. The generic agenda and estimation habits are in the Backend track, section "Backend System Design Walkthroughs".

**Follow-ups they will ask:**
- "Assume cost does not matter"?: Still cover latency and evals; cost returns at scale, and you can say when.
- The interviewer drills into one area?: Follow; the agenda is a default, their questions are the rubric.
- What signals seniority?: Naming the failure mode of each stage and how you would detect it in production.

**Mistakes to avoid:**
- Thirty minutes on prompt wording and none on evals, data permissions or cost.
- Naming a vector database before saying what data exists and who may see it.

## Computer Vision & Document AI [Advanced]

> This comes up for roles that touch invoices, contracts, insurance claims, property listings or engineering drawings: anywhere the input is a picture of a document and the output must be structured data. Interviewers check whether you can break "image in, JSON out" into stages that can each be measured, choose between a specialist vision model and a multimodal LLM, and handle uncertain output. A weak answer sends the image to a multimodal model and asks for JSON. A strong answer normalises the input, uses specialist models where geometry matters, validates output against rules, routes low confidence to a human, and evaluates each stage with the right metric.

### In plain words
Computer vision is teaching software to read pictures the way a person does. To a computer a floor plan is only a grid of coloured dots; the job is to turn those dots into facts such as "the kitchen is a closed shape with these four corners, next to the hall". Think of laying tracing paper over the drawing: first you shade each room, then you trace the walls, then you mark the corners, and finally you write down the coordinates of every shape. Document AI is the same idea for PDFs, invoices and forms: find where things are on the page, read them, and put them into a table or JSON that a program can use.

### From your saved posts
- iiterate_technologies: Floorplan AI turns floor plans (sketches, scans, CAD exports, brochures, many languages) into structured room data: upload an image or PDF, a vision transformer segments the plan into rooms, edge extraction traces walls, corner detection finds where walls meet, and the output is closed polygons with coordinates per room. The speed (under 4 seconds), training data (100,000+ examples) and coverage (20+ floor plan types) are the company's own claims, not independently verified.

### Concepts you must understand
- To a model an image is a grid of pixel values; vision models learn features that build up from edges and textures to whole objects.
- CNNs build features with small sliding filters and a built-in preference for local patterns, which makes them data-efficient; vision transformers cut the image into patches and let every patch attend to every other, which captures global layout but usually needs large-scale pretraining.
- Classification labels the whole image, detection draws boxes, and segmentation labels pixels: semantic (a class per pixel), instance (each object separately) or panoptic (both).
- Geometry post-processing (edge extraction, corner detection, polygon simplification, topology checks) turns a noisy pixel mask into clean shapes a program can trust.
- Pixel coordinates mean nothing until mapped to real units through a scale bar, a dimension label or a known DPI, and the output must state its units.
- Document AI pipelines combine layout detection, OCR, table structure recognition and reading order; multimodal LLMs can extract end to end but are harder to bound and to measure.
- Confidence scores plus validation rules decide what goes to human review, and reviewed corrections become the next round of training data.
- Each stage gets its own metric: IoU for masks and polygons, precision and recall for detected corners or fields, exact match for extracted values, and end-to-end accuracy on the business task.

### Q. Design a system that turns floor-plan images and PDFs into structured room data.
**Short answer (45 seconds):** A staged, asynchronous pipeline where each stage has its own check. Ingest and normalise (rasterise at a fixed DPI, deskew), segment rooms, walls, doors and windows with a vision transformer, extract wall edges and detect corners, turn masks into closed polygons and run topology checks, convert pixels to metres using the scale, then emit JSON validated against a schema. Low-confidence or failed results go to human review, whose corrections feed training. I evaluate with per-room IoU, room-count accuracy and area error.

**Deeper explanation:**

```text
upload (PDF, PNG, JPG) -> object storage, job queue, idempotent on file hash
 -> normalise: vector PDF? read line geometry directly; else rasterise, deskew, denoise
 -> segment (ViT backbone): masks for room, wall, door, window
 -> geometry: wall edges, corner detection, polygon simplification
 -> topology: polygons closed, no overlaps, rooms bounded by walls, doors on walls
 -> scale: scale bar, OCR of dimension labels, or one user-marked length
 -> JSON {units, rooms: [{label, polygon, area_m2, confidence}], source_page}
 -> low confidence or failed check -> review UI -> corrections to training set
```

Two senior details: vector PDFs exported from CAD already contain the wall lines, so parse those paths first and use vision only for scans and photos; and room labels are a separate step, OCR of the text inside each polygon or a classifier on shape and fixtures. Keep every intermediate artefact so a wrong area traces back to its stage, and track the human-correction rate per plan style to see where more training data is needed.

**Follow-ups they will ask:**
- Why not just a multimodal LLM?: Closed polygons need pixel-accurate, repeatable geometry; an LLM helps with labels and text, not coordinates.
- No scale?: Ask the user to mark one known length, or flag areas as unscaled.
- New drawing styles?: Augment training data with varied line weights, hatching and languages, and track metrics per style.

**Mistakes to avoid:**
- Reporting pixel accuracy, which background pixels dominate, so it looks great while rooms are wrong.
- Trusting raw masks without topology checks; a one-pixel gap in a wall merges two rooms.

### Q. CNNs vs vision transformers: what is the difference and when would you use each?
**Short answer (45 seconds):** A CNN slides small learned filters over the image and builds features from local to global layer by layer; its built-in assumptions, locality and translation equivariance, make it data-efficient and affordable at high resolution. A vision transformer cuts the image into fixed-size patches, embeds each as a token and runs self-attention, so any patch can use any other from the first layer; with fewer built-in assumptions it usually needs large-scale pretraining but scales well and captures global layout. I choose by available pretrained checkpoints, data size, resolution and latency budget, not fashion.

**Deeper explanation:**

| | CNN (ResNet, U-Net, ConvNeXt) | Vision transformer (ViT, Swin) |
|---|---|---|
| Core operation | Convolution over local windows | Self-attention over patch tokens |
| Built-in bias | Strong: locality, translation | Weak: learns structure from data |
| Data needs | Works with modest labelled data | Pretrain at scale, then fine-tune |
| High resolution | Cost grows linearly with pixels | Global attention grows quadratically with patch count |

The original ViT paper reported that, trained on mid-sized data, ViT trailed comparable ResNets and pulled ahead only with much larger pretraining; DeiT later narrowed that gap with distillation and heavy augmentation. Since then Swin made high resolution affordable with windowed, hierarchical attention, and ConvNeXt modernised the CNN to compete. For floor plans, enclosed rooms are a global pattern that favours attention, while thin walls demand high resolution, hence hierarchical backbones or tiling.

**Follow-ups they will ask:**
- What is inductive bias?: Assumptions built into the architecture; a CNN assumes nearby pixels belong together and a pattern means the same anywhere.
- What does a multimodal LLM use?: Typically a ViT-style image encoder whose patch embeddings are projected into the language model's token space.
- Which for segmentation?: U-Net with small data; transformer-based models such as SegFormer or Mask2Former when good pretrained weights exist.

**Mistakes to avoid:**
- "Transformers are always better", ignoring data size, resolution and latency.
- Downscaling a large plan to a small input size, which erases thin walls before the model sees them.

### Q. Semantic vs instance vs panoptic segmentation: what are they and how do you measure them?
**Short answer (45 seconds):** Semantic segmentation gives every pixel a class (wall, room, door) but cannot tell two touching rooms apart. Instance segmentation finds each countable object separately with its own mask (room 1, room 2). Panoptic does both: every pixel gets a class, and countable "things" also get an instance id, while amorphous "stuff" such as background gets only a class. The metrics follow: mean IoU for semantic, mask average precision for instance, panoptic quality (PQ) for panoptic.

**Deeper explanation:** Everything starts from intersection over union, the overlap of a predicted and a true mask divided by their combined area:

```python
import numpy as np

def iou(pred: np.ndarray, gt: np.ndarray) -> float:
    inter = np.logical_and(pred, gt).sum()
    union = np.logical_or(pred, gt).sum()
    return float(inter / union) if union else 1.0
```

Mean IoU averages per-class IoU, so a rare class such as doors counts as much as walls. Instance metrics match each predicted mask to a ground-truth mask when IoU passes a threshold, then compute average precision; COCO-style reporting averages AP over thresholds from 0.5 to 0.95. Panoptic quality matches segments at IoU above 0.5 and multiplies segmentation quality (mean IoU of matched pairs) by recognition quality (an F1-style score over true positives, false positives and false negatives). For floor plans, rooms are instances because the output needs room 1 and room 2, while walls behave like stuff, so an instance or panoptic formulation fits. Thin structures also need boundary-aware checks, since a mask can score high IoU while its edges are several pixels off.

**Follow-ups they will ask:**
- Why not pixel accuracy?: Background dominates, so a model that predicts mostly background still scores well.
- How do you get labels?: Polygon annotation in CVAT or Label Studio, with IoU between two annotators as the agreement check.
- Which threshold counts as a match?: 0.5 is the common default; report a stricter one too when geometry must be precise.

**Mistakes to avoid:**
- Using semantic segmentation when downstream code needs separate rooms; touching rooms merge.
- One averaged number that hides a class that always fails.

### Q. When do you use a multimodal LLM versus a specialist vision model for document extraction?
**Short answer (45 seconds):** A multimodal LLM when layouts vary widely, volume is moderate, fields need reading comprehension ("which party is the buyer?") and there is no training data yet. A specialist pipeline (OCR, layout detection, a trained extractor, or a detector or segmenter) when you need exact geometry, high volume at low unit cost, tight latency, per-field confidence, or on-premise processing. Most production systems are hybrid: OCR and layout give text with coordinates, an LLM maps it to the schema, and validators plus human review catch the rest.

**Deeper explanation:**

| Concern | Multimodal LLM | Specialist pipeline |
|---|---|---|
| New layout | Often works zero-shot | Needs labelled examples |
| Coordinates, geometry | Weak and hard to verify | Native |
| Cost at high volume | Image tokens per page add up | Low per page once trained |
| Confidence | Unreliable when self-reported | Per-field scores |
| Failure style | Plausible but invented or misread values | Fails visibly on unseen layouts |

Whichever you pick, validation makes it production grade: cross-field rules (line items sum to the total, dates parse, tax IDs pass their checksum), schema validation, and grounding, where every extracted value must appear in the OCR text of the page, ideally near the expected label. Estimate confidence from agreement between two runs or two models, validator results, and logprobs where the API exposes them. Compare both approaches on the same labelled set with field-level exact match and cost per page before committing.

**Follow-ups they will ask:**
- Data cannot leave the building?: A specialist pipeline or a self-hosted open-weight vision-language model.
- How do you start with no labels?: LLM extraction with validators and human review; the reviewed outputs become training data for a cheaper specialist model later.
- Handwriting?: Measure on your own samples; accuracy varies widely across OCR engines and LLMs.

**Mistakes to avoid:**
- Trusting LLM-extracted amounts and dates without a cross-check.
- Training a custom model before measuring whether a prompt plus validators already meets the bar.

### Q. How do you build a reliable PDF and document parsing pipeline for RAG?
**Short answer (45 seconds):** Treat parsing as its own pipeline with per-page routing and quality gates: digital pages to a layout-aware parser, scanned pages to OCR with layout detection, chart and form pages to a vision model, tables to structure recognition. Everything lands in one document model with headings, reading order, page and bounding box. A per-page quality check routes failures to a fallback, and output is cached by file hash and parser version so a better parser can re-run selectively.

**Deeper explanation:**

```text
file -> sha256 -> parsed before with this parser version? -> reuse
     -> per page: text layer?   -> layout parser (Docling, Unstructured)
                  scanned?      -> OCR + layout detection
                  chart / form? -> vision model description
     -> tables -> structure recognition -> Markdown table + row sentences
     -> blocks {type, text, heading_path, page, bbox, parser_version}
     -> quality gate: garbage-character ratio, empty page, interleaved columns
     -> pass: chunk and embed | fail: fallback parser, then human queue
```

The operational parts make it reliable: queue and workers, idempotency on the file hash, a timeout and memory limit per page because some PDFs hang parsers, a dead-letter queue for poison files, and metrics per source (pages parsed, fallback rate, failures). For a parse-quality eval, keep a small set of hard documents with expected text and tables, and track character error rate, table cell accuracy and retrieval recall on table questions. Parser choice and Docling usage are in this track's section "RAG Fundamentals", the image-first alternative in "Advanced RAG Patterns", and silent parse failures in "RAG Failure Modes & Debugging".

**Follow-ups they will ask:**
- Which OCR?: Tesseract as a free baseline; AWS Textract, Google Document AI or Azure AI Document Intelligence for forms and tables; measure on your own pages.
- Very large PDFs?: Split by page, parse in parallel, merge in page order.
- Parser improved, so re-parse everything?: Only documents whose pages failed the gate or matter most, found through `parser_version` in metadata.

**Mistakes to avoid:**
- One parser for every page with no quality gate.
- Dropping page numbers and boxes, which breaks citations and debugging.

### Practice
- Annotate 20 floor plans or simple diagrams with room polygons in CVAT or Label Studio, run a pretrained segmentation model, and compute per-room IoU.
- Write the polygon step: take a binary mask, find contours with OpenCV `cv2.findContours`, simplify with `cv2.approxPolyDP`, then check closure, minimum area and overlaps.
- Extract fields from 30 invoices with a multimodal LLM and with OCR plus rules; compare field-level exact match, cost per page and the kinds of failures.
- Say it out loud: walk through the floor-plan pipeline in two minutes and name the metric that proves each stage works.

## ML System Design Basics [Advanced]

> Some AI engineer loops, especially at product companies, include a classical ML system design round: recommendations, ranking, search or fraud. Interviewers check that you turn a business goal into an ML objective and a label, design data and features, use a multi-stage architecture with a latency budget, evaluate offline and online, and deploy and monitor the model. A weak answer opens with a model name. A strong answer starts from the objective and the metrics, then the data and labels, then a staged design, and closes with experiments and monitoring.

### In plain words
A recommendation system is like a bookshop assistant in a shop with millions of books. First they grab a few hundred books that might suit you from the right shelves, then they carefully sort that pile by how likely you are to love each one, and finally they shuffle a little so the top of the pile is not ten books by the same author. They learn from what you pick up and what you ignore, and they slip in a few surprises so they can discover new tastes. ML system design is planning that whole shop: where the data comes from, how the assistant learns, how you test that they got better, and how you notice when they get worse.

### From your saved posts
- jam.with.ai (carousel): AI/ML interviews reward designing systems under pressure in 45 minutes more than Kaggle rank, GitHub stars or certificates, and it points to four playlists on the Aced, formerly Exponent, YouTube channel: [youtube.com/@aced_io](https://www.youtube.com/@aced_io).
- Machine Learning Interview Prep playlist (27 videos): end-to-end ML system design with engineers from Google, Waymo and Meta, covering recommendation systems, ranking, embeddings and deployment.
- Data Science Interview Prep playlist (15 videos): case studies, A/B testing, metrics and product analytics.

### Concepts you must understand
- Frame before modelling: business goal, then ML objective, then label; "more purchases" becomes "predict the probability of a purchase given an impression".
- Recommenders are funnels: candidate generation (cheap, high recall, millions down to thousands), ranking (a heavier model on thousands), re-ranking (diversity, freshness, business rules).
- Two-tower models embed users and items separately, so item vectors can be precomputed and searched with approximate nearest neighbour indexes.
- Features are user, item, context and cross features, and must be computed the same way in training and serving, or you get training-serving skew.
- Labels come from logs of what the old system chose to show, so the data carries position bias and selection bias.
- Cold start (new users, new items) is handled with content features, popularity priors and deliberate exploration.
- Offline metrics (AUC, recall@k, nDCG) choose which model deserves an online test; online metrics (CTR, conversion, retention) decide whether it ships.
- A/B tests need a pre-registered primary metric, guardrail metrics, a sample size computed in advance, and no peeking.
- The model shapes the data it will be retrained on, so feedback loops and drift are the default failure, not an edge case.

### Q. Design a recommendation system for a feed or marketplace.
**Short answer (45 seconds):** I clarify the objective (clicks, purchases or long-term retention), the latency budget and the scale, then build a funnel. Candidate generation pulls a few thousand items from several sources: a two-tower embedding model searched with ANN, co-visitation ("bought together"), trending and followed sellers. A ranking model scores those with rich features for the target. Re-ranking applies diversity, freshness, dedupe and business rules. Impressions, positions and actions become the next training data.

**Deeper explanation:**

```text
request (user, context)
 -> candidates: two-tower ANN | co-visitation | trending | followed sellers
 -> merge and filter: out of stock, already seen, blocked           -> thousands
 -> rank: p(click), p(purchase) from user, item, context, cross features -> hundreds
 -> re-rank: diversity, freshness, business rules, ad slots         -> one page
 -> log impressions with position and the actions that followed
```

The towers never see each other's input, which is why they scale: item vectors are computed offline and indexed (HNSW, FAISS or ScaNN), so a request computes only the user vector; training uses clicked items as positives and other items in the batch as negatives. The ranker can afford cross features such as "this user's spend in this category" because it scores thousands of items, not millions; gradient-boosted trees are a strong first ranker. Cold start: a new item gets a content embedding (title, image, category) from the item tower, so it is retrievable on day one; new users get regional favourites plus onboarding choices; an exploration slot gives new items impressions.

**Follow-ups they will ask:**
- Why not one model over all items?: Scoring millions of items with a heavy model per request breaks the latency budget.
- Real-time signals?: Session clicks stream through Kafka into an online feature store such as Redis, with the same definitions used offline.
- How do you avoid a monotonous feed?: Diversity re-ranking such as MMR plus a seen-item filter.

**Mistakes to avoid:**
- Opening with "I would use a neural network" before stating the objective and the label.
- Ignoring position bias and the feedback loop in the training data.

### Q. What are offline and online metrics for a ranking model, and why can they disagree?
**Short answer (45 seconds):** Offline metrics are computed on logged historical data: AUC, log loss and calibration for the scorer, and recall@k, MRR and nDCG@k for the ordered list. Online metrics come from a live A/B test: CTR, conversion, revenue per session, dwell time and retention, with latency and complaint rate as guardrails. They disagree because logs hold only what the old system showed, clicks are a proxy for the business goal, the data is from the past, and live effects such as latency do not exist offline.

**Deeper explanation:**

| Reason | Example | Mitigation |
|---|---|---|
| Selection bias | New model surfaces never-shown, unlabelled items | Exploration bucket, inverse propensity scoring |
| Position bias | Top slots get clicks for being on top | Log position, model it in training, randomise a little traffic |
| Proxy mismatch | Optimising CTR promotes clickbait and retention falls | Multi-objective scoring, long-term metrics as guardrails |
| Time shift | Trained on last month, the season changed | Time-based splits, regular retraining |
| System effects | A heavier model adds latency and engagement drops | Latency guardrail in the test |

Two offline habits prevent most surprises: split by time, because a random split leaks the future, and measure per user or session, because global AUC scores ordering across all users while a feed only needs the right order within one user's page; grouped AUC or nDCG tracks online results better. Metric definitions: this track, section "RAG Failure Modes & Debugging"; the LLM version: MLOps & LLMOps track, section "Evaluation Pipelines in CI/CD".

**Follow-ups they will ask:**
- Which offline metric do you trust?: The one that agreed with online results on past launches; check that history.
- What is inverse propensity scoring?: Weighting each logged outcome by one over the probability the old system showed that item, which must be logged.
- Offline gain, online flat?: Walk the table, starting with position bias and the proxy mismatch.

**Mistakes to avoid:**
- Random train and test splits on time-ordered interaction data.
- Shipping on an offline gain without an online test.

### Q. How do you run and read an A/B test for an AI feature?
**Short answer (45 seconds):** Before starting I write the hypothesis, one primary metric, and guardrail metrics that must not get worse: latency, cost per user, error or complaint rate, escalations. I compute the sample size from the baseline rate and the smallest lift worth shipping, randomise by user, and run for the planned duration over full weekly cycles. When reading, I check the traffic split first, then the primary metric with its confidence interval, then guardrails and pre-planned segments, and I never stop early on a good-looking dashboard.

**Deeper explanation:** Sample size intuition, for about 80 percent power at 5 percent two-sided significance:

```text
n per arm ~ 16 x p(1 - p) / d^2        p = baseline rate, d = absolute lift to detect
baseline 10%, detect +1 point: 16 x 0.09 / 0.0001 = 14,400 users per arm
halve the lift you want to detect and you need four times the users
```

Peeking, checking daily and stopping at the first "win", pushes the false-positive rate well above 5 percent; use a fixed horizon or a sequential method built for repeated looks. A sample ratio mismatch (a planned 50/50 split arriving noticeably uneven) signals an assignment or logging bug and voids the result until explained. Novelty makes a new AI feature look better in week one, so plot the effect by day and for new versus returning users. AI-specific traps: key caches by arm, count token cost per user, and log prompt and model versions per arm. Sticky assignment code is in the MLOps & LLMOps track, section "Evaluation Pipelines in CI/CD".

**Follow-ups they will ask:**
- Too little traffic?: Test only for larger effects, run longer, use a higher-frequency proxy, or rely on offline evals plus shadow traffic.
- Significant but tiny?: Weigh the lift against its cost; statistical significance is not a business case.
- Wins in one segment only?: Treat it as a hypothesis for a new test, since slicing many segments finds chance winners.

**Mistakes to avoid:**
- Stopping the day the p-value drops below 0.05.
- Ignoring a sample ratio mismatch and analysing broken data.

### Q. How do you deploy and monitor an ML model so it does not silently degrade?
**Short answer (45 seconds):** Ship it like a risky release: a versioned model in a registry with its data and feature versions, an offline comparison against the current model on a time-based holdout, shadow traffic to compare predictions and latency, a canary, then an A/B test on the business metric with a fast rollback. Monitor four layers: system, data, model and business. Silent degradation usually starts in the data (a stale feature, a changed upstream schema, a new catalogue) rather than in the model.

**Deeper explanation:**

| Layer | Watch | Example alert |
|---|---|---|
| System | p99 latency, timeouts, fallback rate | Fallback to the popular-items list is rising |
| Data | Null rate per feature, feature freshness, distribution drift | A user activity feature has not updated for an hour |
| Model | Score distribution, calibration, accuracy once labels land | Mean predicted CTR moves while actual CTR does not |
| Business | CTR, conversion, revenue per session by segment | Conversion drops for new users only |

Two design choices make diagnosis possible: log the exact feature values used at serving time, so training-serving skew can be checked offline, and give the system a counted fallback, such as popular items, for when the model or feature store is down. A recommender can degrade with no code change: the catalogue shifts, seasons change, an upstream pipeline renames a field, or its own feedback loop narrows what users see. Drift tests, delayed labels and rollout patterns are in the MLOps & LLMOps track, sections "Model Serving & Deployment Patterns" and "Monitoring ML Systems".

**Follow-ups they will ask:**
- Labels arrive weeks later?: Watch prediction drift and proxy metrics until labels land, then backfill accuracy.
- How do you roll back?: Point the registry alias back at the previous version, which is kept warm.
- Retrain on a schedule or on triggers?: Both; every retrain passes the same gate and canary.

**Mistakes to avoid:**
- Monitoring only infrastructure metrics, which stay green while recommendations rot.
- Not logging serving-time features, so skew cannot be diagnosed.

### Q. How is ML system design different from LLM application design?
**Short answer (45 seconds):** In ML system design you own the model: you define labels, build features, train and retrain; the hard parts are data, labels, training-serving consistency and feedback loops, at high request rates with millisecond budgets. In LLM application design you usually rent a general model: the hard parts are context (retrieval, prompts, tools), judging free-form output, safety of open-ended output and actions, and per-token cost with latency in seconds. The shared core is the same: a clear objective, evals before shipping, staged rollout, monitoring, and feedback into data.

**Deeper explanation:**

| | ML system (ranking) | LLM application (support assistant) |
|---|---|---|
| Model | Trained in-house on your labels | Hosted or open-weight general model, rarely fine-tuned |
| Main lever | Features and labels | Context: retrieval, prompts, tools |
| Output | Score or class | Free text and tool calls |
| Evaluation | AUC, nDCG against labels | Rubrics, LLM judges, task success, human review |
| Latency and cost | Milliseconds, cheap per prediction | Seconds, token cost dominates |
| Typical failure | Silent drift, skew | Hallucination, injection, unsafe actions |

The two are converging: LLM applications are full of classical ML (embeddings for retrieval, rerankers, classifiers for routing and guardrails), and classical systems use LLMs for labels and cold-start content. In an interview, do not answer an ML design question with "call a frontier model", and do not answer an LLM design question without the data, metrics and feedback discipline of an ML engineer.

**Follow-ups they will ask:**
- When would you replace an LLM step with a classical model?: High volume, a narrow task and labelled data, such as intent classification: cheaper, faster and more predictable.
- Adding an LLM to a classical system?: Generating labels, item text and cold-start content features.
- Where does a reranker fit?: It is a learned ranking model inside RAG, evaluated with the same ranking metrics.

**Mistakes to avoid:**
- Treating the two as unrelated skill sets.
- Proposing an LLM call inside a high-volume ranking path with a millisecond budget.

## How LLMs Work, for Engineers

### In plain words
An LLM is a very well-read autocomplete: it reads your text and predicts the next small piece, again and again, until the answer is finished. Those pieces are tokens, chunks of words rather than whole words, so one long word can be several tokens, and you pay for every token that goes in and comes out. The context window is the size of the model's notepad: your instructions, the documents you pasted, the chat so far and the answer it is writing all have to fit on it. Anything not on the notepad does not exist for the model, which is why it cannot see your private data unless you put it there. Inference is just the name for one round of this reading and writing.

## Embeddings & Vector Search

### In plain words
An embedding turns a piece of text into a list of numbers that captures its meaning, like giving every sentence a pin on a giant map where similar meanings sit close together. "How do I reset my password" and "I forgot my login" land near each other even though they share almost no words. Semantic search uses that map: turn the question into a pin, then fetch the stored texts whose pins are closest. A vector database is the map's index, built so that finding the nearest pins among millions stays fast. Keyword search still matters for exact things like order numbers and error codes, which is why many systems use both.

## RAG Fundamentals

### In plain words
Imagine Bob, a smart new hire who knows general facts, like how big Central Park is, but has no idea where your company's IT desk is. Asking him harder will not help; handing him the company documents and letting him look it up will. RAG (retrieval-augmented generation) does exactly that for a model: before it answers, the system searches your documents, puts the most relevant passages into the prompt, and asks the model to answer from them and say where each fact came from. If the search hands Bob the wrong pages, he gives a confident wrong answer, which is why most RAG work is really search work.

## Evaluating LLM Systems

### In plain words
Evaluating an LLM feature is like marking exam answers when there is no single right wording. You collect a set of real questions with notes on what a good answer must contain, run the system on them, and mark each answer pass or fail with a short reason. Then you read the failures and sort them into piles, such as "used an old policy" or "ignored the date", and fix the biggest pile first; that sorting is called error analysis. You rerun the same set after every change, so fixing one pile does not quietly break another.

## Safety, Security & Guardrails

### In plain words
Guardrails are the checks around the model that stop it from saying or doing something it should not, like the rails on a staircase: they do not choose where you walk, they stop a fall. Some checks run before the model (is this message trying to trick it, does it contain a card number), some run after (is the answer safe, on topic and in the right format), and some limit what the model can do at all (read-only tools, a human approval before a refund). The key idea is that text from documents, web pages and emails can carry hidden instructions, so everything the model reads is treated as untrusted. A good design makes a successful trick harmless instead of hoping no trick ever works.
